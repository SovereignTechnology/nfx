# NFX 0.1.3

A network's own scoped relay can now carry its mesh signaling. With `--embed-relay-mesh`,
`nfxd`'s embedded relay also accepts NFX-10 §6 signaling (kind 25050, `nfx-mesh/1`). Pages and
mesh endpoints can then meet on the network's relay as well as on general ones. Nothing else
changes for operators. As before: `nfxd` and `nfx-package`, prebuilt for linux-x64, beside the
source; free video only.

## What changed

- **Scoped relays may carry mesh signaling** (#97; decision record #96). The relay keeps it
  ephemeral: forwarded live, never stored or returned to a later `REQ`.
  - **Opt-in:** `nfxd run --embed-relay <addr:port> --embed-relay-mesh` turns it on. It is off by
    default.
  - **What it accepts:** kind 25050 with exactly one `i` = `nfx-mesh/1`. Every other kind-25050
    event is refused as out of scope.
  - **Checks:** it admits an event only after the checks a reader makes that need no session:
    the tags for the event's type, freshness (60 s back, 30 s ahead), the NIP-01 signature, and
    the room proof against the event's own `P`. It does not decrypt.
  - **Rate limits:** one presence of a type per (sender, room) per 10 s; 64 offers and answers per
    30 s per sender; 36 KiB per event.
  - **Advertised:** the relay's NIP-11 document lists `25050` in `nfx.kinds` and `signaling` in
    `nfx.roles`.
  - **Not scoped to a network.** A signaling event carries no network, and its room key hides
    which video it is. So the relay cannot scope it to its namespaces, and `--allow-creator` does
    not narrow it.
- **The specification.**
  - **NFX-04 §§1–3** gain the MAY above, its limits and its NIP-11 listing. NFX-04 is Frozen@M1,
    so this in-place amendment is recorded as an exception to the freeze rule, in its changelog
    and in `spec/README.md`. It is additive: no artifact or reader changes, and a relay that does
    not admit kind 25050 is exactly as conformant as before.
  - **NFX-10 §6** and **NFX-11**'s L5 level note the option.
- **`nfx-proto`:** `signal::relayable` and `signal::is_nfx_mesh`, a relay's sessionless check of a
  signaling event. `signal::read` now shares its checks with them, with the same verdicts.
- **`nfx-node`:** `ScopedRelay::with_options(namespaces, creators, mesh_signaling)`.
- **Dependencies:** chrono's "unmaintained" notice (RUSTSEC-2026-0543) is ignored, with a date to
  revisit by 2026-12-31 (#95). nfx's own code does not use chrono; it arrives through iroh-blobs,
  wmi (Windows only) and tokio-rustls-acme or serde_with. There is no vulnerability and no fixed
  release.
- **The crates are 0.1.3** (`nfxd`, `nfx-node`, `nfx-media`), and the scoped relay's NIP-11
  document says so.

## Operators: what to change

Nothing: a 0.1.2 command line runs unchanged, and the relay refuses kind 25050 as before unless
you add `--embed-relay-mesh`.

To let your relay carry signaling, add `--embed-relay-mesh` beside `--embed-relay`. Pages and
`--mesh-relay` endpoints may then name it. Name general relays beside it as well: most scoped
relays refuse kind 25050, and a client can tell which do from NIP-11 `nfx.kinds`.

Privacy is as before. Relays, this one included, see room keys, session keys, who signals whom
and when, and every client's IP address, but not the SDP (NFX-10 §6.7).

## Tested

- **A relay and a reader agree** (`a_relay_admits_what_a_reader_would_and_needs_no_session`,
  driven by the signaling vectors).
  - The relay admits every valid event of `mesh-signal.json`.
  - Of `mesh-signal-invalid.json`, it refuses exactly what a reader refuses before decrypting.
  - It carries `other-room` and `not-for-us`, which need a session to judge, and the cases only
    the receiver can reject, since only the receiver decrypts.
- **The relay over a real WebSocket client** (`a_relay_with_mesh_signaling_carries_nfx_mesh_only`).
  - **Off:** kind 25050 is refused and not advertised.
  - **On:** NIP-11 advertises it, and a valid connect reaches a live subscriber.
  - **Rate limits:** a repeat within 10 s is rate-limited; a disconnect and another room are not.
  - **Offers** are admitted without decrypting.
  - **Refused:** another protocol is out of scope, and an event without a room proof is invalid.
  - **Ephemeral:** a fresh `REQ` finds nothing stored.
- **Unchanged paths:** the signal reader and the mesh endpoint's tests (str0m peers, behind a DNAT
  too) pass with the shared checks. `nfxd` refuses `--embed-relay-mesh` without `--embed-relay`.

## What it does not do

As in 0.1.2:
- **No payments.**
- **`nfxd` does not fetch from browsers yet** (#71).
- **`nfxd` behind a symmetric NAT is not covered.**
- **Fetch throughput** is still open (#21).
- **Packaging:** Linux x64 binaries only, not signed by an operating-system vendor. The desktop
  viewer and the web player are built from source.

The public testnet's services and their limits are listed in [testnet.md](../testnet.md).

`sha256sum -c SHA256SUMS` checks that the tarball is intact; it does not say who made it. For that,
the release carries `release-event.json`: a Nostr release notice (kind 30071, `d` = `nfx`) signed
by the SovTech key `npub1s0vtechh66tx7vrwdud8zfyheu9zca7swwfrzd4qu2a4f93mxs6qvn9adx`, listing the
tarball's sha256 and size; the same notice is on Nostr relays. To check it, with Node 22.18 or
newer and a checkout of nutflix-pear (whose release scripts sign and verify both projects'
notices):

```sh
git clone https://github.com/SovereignTechnology/nutflix-pear.git && cd nutflix-pear
npm ci --ignore-scripts
node scripts/release-verify.mjs release-event.json --d nfx nfx-0.1.3-linux-x64.tar.gz
```

It checks the signature, that the key is SovTech's, that the notice is NFX's, and the file's size
and sha256. The release is built by `.github/workflows/release.yml` from the tagged commit in the
pinned `rust:1.98.0-bookworm` image, `--locked`, with the commit's timestamp and the build paths
remapped.
