# NFX 0.1.4

The embedded relay no longer forgets its manifests when it restarts, and a client has a
decentralized way to find a STUN server. As before: `nfxd` and `nfx-package`, prebuilt for
linux-x64, beside the source; free video only.

## What changed

- **An embedded relay keeps its manifests across a restart** (#115, #116; decision record 0106).
  Until now `nfxd --embed-relay` held every manifest in memory, so a restart emptied it and a
  seeder that resolves its videos from that relay waited in `Resolving` until a creator published
  again. On the reference deployment that caused two outages, one of 5.5 hours.
  - **With `--state`,** the relay writes each accepted kind-38504 manifest to
    `<state>/relay-manifests/` (mode 0700, one file per address) and serves them again after a
    restart. Without `--state` it behaves as before.
  - **A file grants nothing.** On load every event is checked again (id, signature, expiry) and
    put through this run's admission rules, so a creator no longer on `--allow-creator` is not
    served. A withdrawn manifest stays withdrawn.
  - **Bounded and safe to lose.** At most 20,000 manifests and 64 KiB each. Writes are durable
    (fsync, rename). A damaged file is logged and removed, and never stops a start. One writer per
    directory: a second relay on it logs why and runs in memory.
  - **Only manifests are kept,** never beacons or signaling.
- **STUN servers can be found over Nostr** (#107, #117, #118; decision records 0107 and 0108;
  NFX-04 §§1 and 3 and NFX-10 §1 are amended in place, recorded as exceptions to the freeze rule).
  A STUN server can be announced, and a client picks servers by one rule:
  1. its own servers first;
  2. then the STUN servers of the relays it signals through: a relay whose own host answers STUN
     says so in its NIP-11 document, `nfx.stun_port` (1024 to 65535, only on a relay that lists
     kind 25050), and the client asks `stun:<relay host>:<port>`. The relay already sees the
     client's address, so its STUN server learns only the UDP port;
  3. then the `stun` endpoint of a live, verified beacon of the video **signed by its creator**;
  4. any other server a Nostr event names only as a fallback, when the servers above gave no mapping
     or the client has none: the `stun` endpoint of a seeder it is already signaling with;
  5. at most 4 servers, global unicast addresses only, ports 1024 and up.
  - **A server named by one key is never used on its own.** Keys are free, so counting keys proves
    nothing. A STUN service announcement (kind 33478, 24 h) is a directory entry that is never
    used automatically.
  - **`nfxd stun --bind <ip:port> [--public <ip:port>] [--announce …]`** runs a STUN server and
    nothing else: a Binding responder, rate limited, nothing about a client logged. With
    `--announce` it signs and sends the announcement now and every 12 h.
  - **`--embed-relay-stun-ads`** lets the embedded relay carry those announcements.
  - **`--embed-relay-stun-port <port>`** puts `nfx.stun_port` in the relay's NIP-11 document. It
    needs `--embed-relay`. `nfxd` does not check that anything answers there: run `--stun` or
    `nfxd stun` on that port.
  - **The mesh endpoint** asks, after its own `--mesh-stun`, the creator's beacon `stun` endpoint
    for the videos it serves. `--mesh-stun-from-nostr=false` turns that off. It does not read relays'
    `stun_port`.
  - **Web player library:** opt-in `NostrSignaling.relayStun` (it reads each relay's NIP-11 once,
    never waits for it, and refuses loopback and private hosts), `selectStun(own, relays, creator)`
    and the fallback API. The test vectors are `spec/test-vectors/stun-select.json` and
    `relay-stun.json`.
- **`nfxd` never panics on a closed stdout or stderr** (#112, fixes #93). `nfxd key show f | head
  -n 1` could exit 101 depending on scheduling. A reader that left is now a normal end.
- **Stats for nerds** (#102): every player shows where its bytes come from (peers, the selected
  candidate pair, origin bytes), in the web library, the test player and the desktop viewer.
- **Opt-in remote candidate filter** (#108): `remoteCandidates: 'global'` in the web library's
  Nostr signaling keeps only UDP candidates at global unicast IP literals. The default is
  unchanged.
- **Dependencies:** `url` 2.5.9 (RUSTSEC-2026-0592, #111). The `heapless` unsound notices
  RUSTSEC-2026-0574 to -0582 are ignored with a date to revisit, 2026-12-31 (#110): none of the
  affected code is reachable from nfx.
- **The crates are 0.1.4** (`nfxd`, `nfx-node`, `nfx-media`), and the scoped relay's NIP-11
  document says so.

## Operators: what to change

Nothing, for a 0.1.3 command line to keep working. Two things happen on their own:

- **A relay run with `--state` now writes to `<state>/relay-manifests/`.** On an open relay,
  anonymous publishers can make it write up to about 1.3 GiB; `--allow-creator` removes that. A
  full disk is logged and the relay keeps serving from memory.
- **A mesh endpoint may now use a STUN server from a creator's beacon** after its own. Turn that
  off with `--mesh-stun-from-nostr=false`.

To advertise your host's STUN server on your relay, add `--embed-relay-stun-port <port>` and run
a STUN server on that UDP port.

## Tested

- **Relay persistence:** `relay_persist` (the store, over real files, including damage, limits,
  deletions and the directory lock) and `relay_restart` (the real `nfxd` binary restarted over the
  same `--state`).
- **STUN selection:** one rule, two implementations, one set of vectors. `nfx-proto` and the web
  library's `selectStun` both pass `stun-select.json` (`relay-stun.json` is checked by the web
  library), including the fallback cases and the refusals (private, loopback, port under 1024, a
  name that is not global).
- **Closed pipes:** the real binary run with the read end closed before it starts, for stdout and
  for stderr.
- CI on this commit: the workspace tests, the web player's unit and engine suites, `tsc`, the NAT
  matrix, coverage, `cargo deny` and the lock check.

## What it does not do

- **Native nodes do not read relays' `stun_port`.** The web library does, opt-in. The mesh endpoint
  uses its own servers and creators' beacons.
- As in 0.1.3: **no payments**; **`nfxd` does not fetch from browsers yet** (#71); **`nfxd` behind a
  symmetric NAT is not covered**; fetch throughput is still open (#21).
- **Packaging:** Linux x64 binaries only, not signed by an operating-system vendor. The desktop
  viewer and the web player are built from source.

The public testnet's services and their limits are listed in [testnet.md](../testnet.md).

## Verify

`sha256sum -c SHA256SUMS` checks that the tarball is intact; it does not say who made it. For that,
the release carries `release-event.json`: a Nostr release notice (kind 30071, `d` = `nfx`) signed
by the SovTech key `npub1s0vtechh66tx7vrwdud8zfyheu9zca7swwfrzd4qu2a4f93mxs6qvn9adx`, listing the
tarball's sha256 and size; the same notice is on Nostr relays. To check it, with Node 22.18 or
newer and a checkout of nutflix-pear (whose release scripts sign and verify both projects'
notices):

```sh
git clone https://github.com/SovereignTechnology/nutflix-pear.git && cd nutflix-pear
npm ci --ignore-scripts
node scripts/release-verify.mjs release-event.json --d nfx nfx-0.1.4-linux-x64.tar.gz
```

It checks the signature, that the key is SovTech's, that the notice is NFX's, and the file's size
and sha256. The release is built by `.github/workflows/release.yml` from the tagged commit in the
pinned `rust:1.98.0-bookworm` image, `--locked`, with the commit's timestamp and the build paths
remapped.
