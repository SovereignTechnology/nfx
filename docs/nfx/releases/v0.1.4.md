# NFX 0.1.4

The embedded relay no longer forgets its manifests when it restarts, and a client has a
decentralized way to find a STUN server. A seeder no longer names its LAN, VPN or tailnet addresses
to public relays, a viewer can ask who seeds a video instead of waiting for the next beacon, and
players and seeders ride out a dead relay or STUN server. As before: `nfxd` and `nfx-package`,
prebuilt for linux-x64, beside the source; free video only.

## What changed

- **An embedded relay keeps its manifests across a restart** (#115, #116; decision record 0106).
  Until now `nfxd --embed-relay` held every manifest in memory, so a restart emptied it and a
  seeder that resolves its videos from that relay waited in `Resolving` until a creator published
  again. On the reference deployment that caused two outages, one of 5.5 hours.
  - **With `--state`,** the relay writes each accepted kind-38504 manifest to
    `<state>/relay-manifests/` (mode 0700, one file per address) and serves them again after a
    restart. Without `--state` it behaves as before.
  - **A file grants nothing.** On load every event is checked again (id, signature, expiry) and
    put through this run's admission rules, so a creator no longer on `--allow-creator` is not
    served. A withdrawn manifest stays withdrawn.
  - **Bounded and safe to lose.** At most 20,000 manifests and 64 KiB each. Writes are durable
    (fsync, rename). A damaged file is logged and removed, and never stops a start. One writer per
    directory: a second relay on it logs why and runs in memory.
  - **Only manifests are kept,** never beacons or signaling.
- **STUN servers can be found over Nostr** (#107, #117, #118; decision records 0107 and 0108;
  NFX-04 §§1 and 3 and NFX-10 §1 are amended in place, recorded as exceptions to the freeze rule).
  A STUN server can be announced, and a client picks servers by one rule:
  1. its own servers first;
  2. then the STUN servers of the relays it signals through: a relay whose own host answers STUN
     says so in its NIP-11 document, `nfx.stun_port` (1024 to 65535, only on a relay that lists
     kind 25050), and the client asks `stun:<relay host>:<port>`. The relay already sees the
     client's address, so its STUN server learns only the UDP port;
  3. then the `stun` endpoint of a live, verified beacon of the video **signed by its creator**;
  4. any other server a Nostr event names only as a fallback, when the servers above gave no mapping
     or the client has none: the `stun` endpoint of a seeder it is already signaling with;
  5. at most 4 servers, global unicast addresses only, ports 1024 and up.
  - **A server named by one key is never used on its own.** Keys are free, so counting keys proves
    nothing. A STUN service announcement (kind 33478, 24 h) is a directory entry that is never
    used automatically.
  - **`nfxd stun --bind <ip:port> [--public <ip:port>] [--announce …]`** runs a STUN server and
    nothing else: a Binding responder, rate limited, nothing about a client logged. With
    `--announce` it signs and sends the announcement now and every 12 h.
  - **`--embed-relay-stun-ads`** lets the embedded relay carry those announcements.
  - **`--embed-relay-stun-port <port>`** puts `nfx.stun_port` in the relay's NIP-11 document. It
    needs `--embed-relay`. `nfxd` does not check that anything answers there: run `--stun` or
    `nfxd stun` on that port.
  - **The mesh endpoint** asks, after its own `--mesh-stun`, the creator's beacon `stun` endpoint
    for the videos it serves. `--mesh-stun-from-nostr=false` turns that off. It does not read relays'
    `stun_port`.
  - **Web player library:** opt-in `NostrSignaling.relayStun` (it reads each relay's NIP-11 once,
    never waits for it, and refuses loopback and private hosts), `selectStun(own, relays, creator)`
    and the fallback API. The test vectors are `spec/test-vectors/stun-select.json` and
    `relay-stun.json`.
- **A seeder names its private addresses only to relays on its own networks** (#128, #134, fixes
  #132; decision record 0114; NFX-03 §4 gains a dated publisher rule, readers are unchanged).
  Until now a seeder behind a NAT with no `--iroh-external` put every address iroh binds on (LAN,
  VPN, tailnet) in its beacons, on every relay. Now `nfxd` classes each relay by the address it
  actually connected to:
  - a relay reached at a **public** address hears beacons whose iroh endpoint (`addrs` and every
    ticket) names only the iroh relay, public addresses and `--iroh-external`;
  - a relay reached at an address of the node's **own host or networks** (loopback, RFC 1918,
    100.64.0.0/10, link-local, fc00::/7: the embedded relay, a relay on the LAN or tailnet) hears
    every address, as before, in a beacon signed apart, so a viewer on that network still dials
    the node directly;
  - it fails closed: a relay reached through a proxy, one with live connections of both classes,
    and an `--embed-relay` bound to `0.0.0.0`/`[::]` count as public, and a full beacon is refused
    by any connection to a public address;
  - NFX-17 answers and gossip envelopes carry the public beacon only. With `--iroh-external` set,
    nothing changes.
  - **`nfxd run --public-addrs-only`** publishes the public list everywhere, for a node whose
    loopback or private relay is itself published to the internet (behind a TLS proxy or a DNAT),
    which `nfxd` cannot detect. In the library: `NodeConfig::public_addrs_only`,
    `nfx_node::relay_class`.
- **Seeder lookup** (#119, closes #113; draft NFX-17, decision record 0105). A viewer could wait up
  to a minute on "Finding seeders…", because beacons are ephemeral and a newcomer waits for the
  next one. Now a viewer can ask who seeds a video (kind 20465, `ask`), and each seeder answers at
  once with its own complete signed beacon (`tell`), which the viewer checks as any beacon (NFX-03).
  - **`nfxd` answers asks** for the videos it announces, within budgets per viewer, per video and
    overall; `--no-lookup` turns it off. Beacons now last 60 s and are re-sent every 30 s.
  - **The embedded relay carries kind 20465 only with `--embed-relay-lookup`, off by default.** A
    scoped relay may list the kind only once NFX-04 allows it, which needs its own decision record
    first: do not turn it on on a scoped relay yet.
  - **Every viewer fetches each file from all the sources it knows,** ordered by what it can check
    (the creator's own beacon, trusted keys, open sources, then the page's last resort; how many
    keys name an origin never ranks it), from one source's bytes per file, leaving a source that
    stalls, runs slow or sends bytes that do not verify.
  - **Web player library:** `watchEndpoints(..., { ask: true })` returns `ask()`, to call when the
    viewer presses Play; `Session.addSources`. The demo page asks only with `?ask=1`.
- **Surviving a dead relay or STUN server** (#130; decision record 0111). On 2026-11-26 the path to
  relay.nutflix.xyz's host dropped twice, and pages and nodes that needed that relay or that host's
  STUN server stopped finding seeders until restarted.
  - **Web player library:** beacon subscriptions reopen whenever they end (1 s, doubling to 30 s),
    and ICE gathering ends 300 ms after the first server-reflexive candidate, so a STUN server that
    never answers no longer holds every connection for 5 s.
  - **`nfxd`:** `--mesh-stun` takes `host:port` as well as `ip:port` (resolved once at start; a
    name that does not resolve is skipped with a note). Each video's beacon goes to every `--relay`
    within a share of that relay (NFX-03 §7): at most 20 beacons a minute per relay, past 10 videos
    they take turns, and a `rate-limited:` or `blocked:` answer pauses that relay for 1 minute,
    doubling to 30.
- **Peers first, in the web player library** (#126; decision record 0109; NFX-10 §1 and §6.8
  reworded, nothing on the wire changes). `open({ segmentSource })`: `https-first` (as before, the
  default), `peers-then-https` (HTTPS only as a rescue, after `peerWaitMs`, default 4000) or
  `peers-only`; `Session.setSegmentSource` changes it while playing. A WebRTC check at the start of
  a session with a mesh says when the browser cannot reach any peer (`stats().mesh.webrtc` is
  `blocked`, with a `mesh` event) instead of showing an origin as the only source with no reason.
  New events and stats: `waiting`, `resumed`, `rescue`, `MeshStats.source`, `rescues`, `startup`.
- **The mesh says why a link never opened** (#122, part of #94): `nfxd` logs each mesh connection
  that never opens with the stage it reached (no answer, answer refused, no ICE pair, ICE up but no
  DTLS, DTLS up but no data channel) and the kinds of candidate each side named, counted, never
  addressed (`host 1, srflx 2`).
- **NFX-18, keeping and seeding what is watched** (#129; decision record 0110, which amends the
  2026-09-24 audit's L4): a new Draft, optional spec for viewers that keep and seed what their user
  watches, and NFX-12's `hyperdht` endpoint gains the optional `renditions` the `https` endpoint
  has. Spec, schema and test vectors only: no implementation ships in this release.
- **`nfxd` never panics on a closed stdout or stderr** (#112, fixes #93). `nfxd key show f | head
  -n 1` could exit 101 depending on scheduling. A reader that left is now a normal end.
- **Stats for nerds** (#102): every player shows where its bytes come from (peers, the selected
  candidate pair, origin bytes), in the web library, the test player and the desktop viewer.
- **Opt-in remote candidate filter** (#108): `remoteCandidates: 'global'` in the web library's
  Nostr signaling keeps only UDP candidates at global unicast IP literals. The default is
  unchanged.
- **Dependencies:** `url` 2.5.9 (RUSTSEC-2026-0592, #111). `nostr-sdk` and `nostr` 0.45.6 (#123):
  crates.io yanked `nostr-sdk` 0.45.0 to 0.45.5, whose verification cache could take a tampered
  event for an already verified one, and `nostr` 0.45.6 compares the NIP-44 v2 HMAC in constant time. The `heapless` unsound notices
  RUSTSEC-2026-0574 to -0582 are ignored with a date to revisit, 2026-12-31 (#110): none of the
  affected code is reachable from nfx.
- **The crates are 0.1.4** (`nfxd`, `nfx-node`, `nfx-media`), and the scoped relay's NIP-11
  document says so.

## Operators: what to change

Nothing, for a 0.1.3 command line to keep working. Two things happen on their own:

- **A relay run with `--state` now writes to `<state>/relay-manifests/`.** On an open relay,
  anonymous publishers can make it write up to about 1.3 GiB; `--allow-creator` removes that. A
  full disk is logged and the relay keeps serving from memory.
- **A mesh endpoint may now use a STUN server from a creator's beacon** after its own. Turn that
  off with `--mesh-stun-from-nostr=false`.
- **A seeder behind a NAT with no `--iroh-external` stops naming its private addresses to public
  relays.** Viewers on the internet reach it through the iroh relay or its public addresses, as
  they already could; viewers on its own network still get every address through a relay there.
  If your loopback or LAN relay is itself published to the internet, add `--public-addrs-only`.
- **`nfxd` answers seeder lookups** for what it announces (`--no-lookup` to stop), its beacons last
  60 s and are re-sent every 30 s, and it sends at most 20 beacons a minute to each `--relay`.

To advertise your host's STUN server on your relay, add `--embed-relay-stun-port <port>` and run
a STUN server on that UDP port.

## Tested

- **Relay persistence:** `relay_persist` (the store, over real files, including damage, limits,
  deletions and the directory lock) and `relay_restart` (the real `nfxd` binary restarted over the
  same `--state`).
- **STUN selection:** one rule, two implementations, one set of vectors. `nfx-proto` and the web
  library's `selectStun` both pass `stun-select.json` (`relay-stun.json` is checked by the web
  library), including the fallback cases and the refusals (private, loopback, port under 1024, a
  name that is not global).
- **Closed pipes:** the real binary run with the read end closed before it starts, for stdout and
  for stderr.
- **Relay classing:** `relay_class` over every address block (loopback, RFC 1918, 100.64/10,
  link-local, ULA and IPv4-mapped private; documentation, NAT64, 6to4, Teredo and multicast count as
  public) and against a real local relay (a private-only event never leaves on a public
  connection), and the real daemon: a relay it reaches at a public address never hears a private
  address, while the embedded relay on loopback does.
- **Seeder lookup:** the nfx-proto, nfx-node, nfxd and nfx-wasm suites, and the vectors
  `spec/test-vectors/lookup.json` and `lookup-invalid.json` for the ask and tell builders and readers. **Relay share:** `relay_share` unit tests, and
  `--mesh-stun` name resolution. **Player:** the web library's 758 unit tests.
- CI on this commit: the workspace tests, the web player's unit and engine suites, `tsc`, the NAT
  matrix, coverage, `cargo deny` and the lock check.

## What it does not do

- **`nfxd` cannot yet tell a scoped relay from a general one,** so the general beacon bound applies
  to every `--relay` (the safe direction: a scoped relay gets less than NFX-04 allows). Lookup
  answers do not yet draw from the same share; that comes in 0.1.5.
- **No viewer keeps or seeds what it watched yet:** NFX-18 is a spec in this release. The desktop
  viewer does not set `public_addrs_only` yet.
- **Native nodes do not read relays' `stun_port`.** The web library does, opt-in. The mesh endpoint
  uses its own servers and creators' beacons.
- As in 0.1.3: **no payments**; **`nfxd` does not fetch from browsers yet** (#71); **`nfxd` behind a
  symmetric NAT is not covered**; fetch throughput is still open (#21).
- **Packaging:** Linux x64 binaries only, not signed by an operating-system vendor. The desktop
  viewer and the web player are built from source.

The public testnet's services and their limits are listed in [testnet.md](../testnet.md).

## Verify

`sha256sum -c SHA256SUMS` checks that the tarball is intact; it does not say who made it. For that,
the release carries `release-event.json`: a Nostr release notice (kind 30071, `d` = `nfx`) signed
by the SovTech key `npub1s0vtechh66tx7vrwdud8zfyheu9zca7swwfrzd4qu2a4f93mxs6qvn9adx`, listing the
tarball's sha256 and size; the same notice is on Nostr relays. To check it, with Node 22.18 or
newer and a checkout of nutflix-pear (whose release scripts sign and verify both projects'
notices):

```sh
git clone https://github.com/SovereignTechnology/nutflix-pear.git && cd nutflix-pear
npm ci --ignore-scripts
node scripts/release-verify.mjs release-event.json --d nfx nfx-0.1.4-linux-x64.tar.gz
```

It checks the signature, that the key is SovTech's, that the notice is NFX's, and the file's size
and sha256. The release is built by `.github/workflows/release.yml` from the tagged commit in the
pinned `rust:1.98.0-bookworm` image, `--locked`, with the commit's timestamp and the build paths
remapped.
